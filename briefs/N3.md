# N3 Data and learning

You are the **N3 Data and learning** session for **Lab Rotation**, our entry in today's
Multiplayer AI Hackathon (Finch, AWS Builder Loft, Mon Nov 23 2026). We submit by
**5:50 PM**. Nived supervises you; work without asking to continue.

**The product.** A flight simulator for an analyst's first weeks. A panel of AI
scientists (Dr. Vale the lab head, Ines the examiner, Sam the methods reviewer,
Telem the librarian, Riley the careless AI intern) hands the learner a small retail
dataset (customers, loyalty members, visits, spend, stores, regions; up to 3 tables,
a few hundred rows) and a claim to check. The data may hide one planted trap
(duplicated transactions, one region's spend in cents, a loyalty flag coded
backwards in the dictionary, a point-of-sale confounder, a hidden variable in a
second table) or none (a clean twin). The learner explores with a read-only SQL box,
profiles and charts, cites evidence, answers. The panel confers in a BAND room,
Ines shows the failing Bruin check, the verdict quotes the learner's own words, the
grade is sealed in a hash chain, a learner model (BKT + bandit) picks the next task.
The 2D lab floor (and a three.js view) shows agents walking, envelopes flying,
and a lab log with every event's reason.

## Your job
You own the tasks, the SQL runner, the Bruin pipeline and the learner model.

**Task generator (`lab/tasks/`), written fresh.** Retail chain: `stores` (region,
pos_version), `customers` (loyalty_member, home_store), `visits` (spend, items,
date), optionally a second-table hidden variable. Up to 3 tables, a few hundred rows.
- Five traps: `duplicate_rows`, `unit_mismatch` (one region in cents),
  `dictionary_flip` (loyalty flag coded backwards in the data dictionary),
  `confounder` (a POS version that shifts spend and differs by group),
  `hidden_variable` (the deciding column sits in a second table); and clean twins
  (`none`, the claim holds).
- Three tiers: 1 one trap in one table; 2 a trap plus a decoy; 3 a trap spanning
  two tables.
- Each task has a careful analysis (the key) and a careless one (Riley's). **Keep a
  draw only when the careful analysis gets it right and the careless one gets it
  wrong** (clean twins: careless suspicion must not score).
- Output per task: the public part in the exact shape of
  `contract/mock_task/task.json` plus CSVs, and a sealed key (trap, correct verdict,
  careful and careless answers, check ids) that never leaves the server.
- A task bank pre-generated at several seeds per skill and tier, so a session
  never waits. API for N1: `lab.tasks.bank.load(task_id)`, `pick(skill, tier, seen)`.
- Real retail parameters come from N2's Glasser client (fall back to fixed values).

**`lab/workspace_sql.py`:** `run_query(task, sql)` read-only over that task's
public tables only (in-memory DuckDB, no file access, row cap 500, 3 s timeout,
one statement, no `COPY/ATTACH/INSTALL/read_csv` etc.), `table_rows`, `profile`
(shapes in `contract/api.md`). Test the escapes.

**Bruin (`bruin/`).** Already set up: `bruin run bruin` works; DuckDB file
`data/warehouse.duckdb` (do not name it `lab.duckdb`: the catalog clashes with the
`lab` schema). Bruin, the duckdb CLI and the Python package are all DuckDB 2.0.1 and
read each other's files; pin `duckdb==2.0.1` in any Bruin Python asset's
requirements. Replace `bruin/assets/smoke.sql` with:
- ingestr loads of task tables, session events and bench results;
- one quality check per trap (unique over measured columns; per-region range;
  companion-column check for the dictionary; within-batch comparison; column
  exists across tables). The failing check is Ines's evidence: give N1 a function
  that runs the checks for a task and returns `check.result` data;
- assets `skill_attempts`, `bkt_mastery` (Python asset), `session_scores`,
  `bench_results` (N4 writes `data/bench/*.csv`; you load it).

**Learner model (`lab/learner/`).** Bayesian Knowledge Tracing per skill (the five
traps plus `trust_clean`; prior, learn, slip, guess), run as the Bruin Python asset;
a Thompson-sampling bandit over skill and tier weighted to low mastery, with a
rules fallback; `mastery(learner)` in the `api.md` shape; `pick_next` returns the
reason in words.

Tests in `tests/test_n3_*.py` (keep filter, SQL safety, BKT updates, bandit).
